01 / FOUNDATION

The Loop Owns Nothing But You

open: Program.cs · BreakoutGame.cs

The single most important thing to understand about MonoGame: it is a library, not an engine. An engine owns a world — a scene tree, an editor, objects that update and draw themselves — and calls your scripts when it feels like it. MonoGame is a library with a heartbeat: your executable starts, you construct one Game object, and Run() pumps a loop until you call Exit(). Nothing exists unless your code creates it; nothing appears on screen unless your code drew it this frame.

Program.csthe entire entry point
using var game = new Breakout.BreakoutGame();
game.Run();

The using var guarantees the window and GL context are torn down when Main exits — cleanup an engine would do invisibly, written out in plain sight.

The four lifecycle overrides

OverrideRunsYour job inside it
Initialize()once, after the graphics device existsnon-content setup — and base.Initialize() is what calls LoadContent()
LoadContent()oncecreate the SpriteBatch, load fonts / textures / sounds
Update(GameTime)every tick (60 Hz here, §02)read input, advance the simulation
Draw(GameTime)every frameredraw the entire world from scratch — nothing persists on screen between frames
GOTCHA

The base.* calls do real work. Delete base.Initialize() and LoadContent() silently never runs. These are not the polite-but-optional super calls of many frameworks — here base is load-bearing.

DESIGN NOTE

BreakoutGame is deliberately thin — it owns the window, the loop, the SpriteBatch and the virtual screen, then delegates to GameStateManager. It is also the only class nothing else references: the application shell knows about gameplay, gameplay never knows about the shell. Search the repo for BreakoutGame — it appears only in Program.cs. That property is worth defending in any codebase.

02 / TIME

Fixed Timestep & Delta — Why Both

open: BreakoutGame.cs (constructor, Update)

With IsFixedTimeStep = true (the default, stated explicitly in the constructor on purpose), MonoGame calls Update() on a fixed 60 Hz clock: the simulation ticks at a steady, predictable rate no matter how fast the machine renders, which is what keeps physics deterministic — the ball takes the same path on every PC. So why does every movement line still multiply by delta?

BreakoutGame.csextracting delta from GameTime
float dt = (float)gameTime.ElapsedGameTime.TotalSeconds;
_states.Update(dt, _input);

Two reasons. First, when a frame runs long, MonoGame runs catch-up Updates, and ElapsedGameTime stays honest about real elapsed time. Second, position += velocity * dt keeps working if the tick rate ever changes — hardcoding per-tick speeds couples gameplay to the clock, and "the ball moves 5 px per Update" becomes a bug the day the game runs at 144 Hz.

GOTCHA

ElapsedGameTime is a TimeSpan, not a float. The cast (float)…TotalSeconds is the idiom; forget it and the compiler reminds you, use .Seconds (an int!) and it silently breaks.

WORTH KNOWING

Many frameworks hand you a bare delta float. MonoGame hands you a GameTime object carrying both ElapsedGameTime (your delta) and TotalGameTime (time since launch — handy for pulsing effects, see PowerUp.Draw which tracks its own age instead).

03 / RENDERING

SpriteBatch & the 1×1 Pixel Trick

open: Source/Systems/SpriteBatchExtensions.cs · any Draw method

All 2D drawing goes through SpriteBatch: call Begin(), queue textured quads, call End(), and the batch submits them to the GPU efficiently. There is no retained canvas — and there is also no draw_rect. MonoGame draws textures, full stop. The universal workaround: a one-pixel white texture, stretched and tinted.

Source/Systems/SpriteBatchExtensions.csthe whole trick
_pixel = new Texture2D(device, 1, 1);
_pixel.SetData(new[] { Color.White });

public static void DrawRect(this SpriteBatch spriteBatch, Rectangle rect, Color color)
    => spriteBatch.Draw(_pixel, rect, color);

The GPU does not care that the source texture is one pixel — sampling it at any size yields flat white, and the tint color does the rest. Every paddle, brick, ball, particle and letterbox bar in this game is that one texture. The whole game ships with zero image files.

GOTCHA

SpriteBatch.Begin() defaults to linear filtering. Scale anything up and it smears. This project passes samplerState: SamplerState.PointClamp at both Begin sites (world pass and present pass) — that's the "crisp pixels" switch.

MENTAL MODEL

In a scene-graph engine, a rectangle node persists in a tree and draws itself forever. Here, if Draw doesn't issue the call this frame, the thing does not exist on screen. Drawing is a verb, never a noun.

DESIGN NOTE

Premultiplied alpha: Color.Black * 0.65f (the game-over dim layer) and p.Color * life (particle fade) multiply RGB and A together, which is what SpriteBatch's default blend state expects. Setting only the alpha channel by hand is the classic "why does my fade look wrong" bug.

04 / ASSETS

Two Ways to Load a Thing

open: Content/Content.mgcb · Content/Fonts/Hud.spritefont · Source/Systems/LevelLoader.cs · Breakout.csproj

This project deliberately demonstrates both asset routes, because choosing between them is a real decision you'll make on every MonoGame project.

Route 1 — the Content Pipeline (the font)

The pipeline compiles assets at build time into .xnb binaries: textures into GPU formats, fonts into rasterized glyph atlases. Content.mgcb is its plain-text manifest (the MGCB Editor is just a GUI over it). Asset names are path-without-extension relative to Content/:

BreakoutGame.csloading a compiled asset
_font = Content.Load<SpriteFont>("Fonts/Hud");
GOTCHA

There is no "just draw text" in MonoGame. Hud.spritefont is an XML description (font family, size, character range) that the pipeline bakes into a glyph atlas. No SpriteFont, no DrawString.

Route 2 — runtime loading (the levels)

The level grid gains nothing from being compiled, and keeping it plain text means editing a level requires no rebuild. So it bypasses the pipeline entirely:

Source/Systems/LevelLoader.csplatform-safe runtime file access
using Stream stream = TitleContainer.OpenStream("Content/Levels/level01.txt");
using var reader = new StreamReader(stream);
GOTCHA

The pipeline only copies what it builds. Runtime-loaded files need their own CopyToOutputDirectory entry in the .csproj — without it the game works on your machine right up until you wonder why a fresh clone crashes.

MENTAL MODEL

Every big engine has an asset import step; most hide it behind drag-and-drop and a cache folder you never open. The Content Pipeline is that step made visible and put under your control — and TitleContainer is the escape hatch for files you want raw.

05 / INPUT

Input Is a Snapshot, Not an Event

open: Source/Systems/InputHelper.cs

MonoGame has no input events, no signals, no action map. Keyboard.GetState() returns a snapshot of which keys are down right now, and that's all you get. "Is the key down" is trivial. "Was it just pressed" requires memory:

Source/Systems/InputHelper.csthe current/previous pattern
public void Update(VirtualScreen virtualScreen)
{
    _previousKeyboard = _keyboard;
    _previousMouse = _mouse;
    _keyboard = Keyboard.GetState();
    _mouse = Mouse.GetState();
    // ...
}

public bool WasKeyJustPressed(Keys key)
    => _keyboard.IsKeyDown(key) && _previousKeyboard.IsKeyUp(key);

Down now + up last frame = pressed this frame. That two-line comparison is exactly what any engine's built-in "just pressed" query does internally. Every polling-based codebase grows this wrapper; the discipline is calling Update() exactly once per tick, before anyone reads input.

DESIGN NOTE

MouseX returns virtual coordinates (§08 transform applied) so gameplay never learns the window size exists — but MouseMoved compares raw window positions, because the virtual transform rounds to ints and that rounding could register phantom movement. Two coordinate spaces, each used where it's correct.

WORTH KNOWING

There is also no action map — no built-in layer that turns "the jump action" into "Space or W or gamepad A". The moment you want rebindable controls, you build a dictionary from action name to Keys[] on top of this same helper (Appendix C has it as an exercise).

06 / SIMULATION

AABB Collision & the Paddle That Aims

open: Source/Systems/CollisionHelper.cs · Source/States/PlayingState.cs · Source/Entities/Ball.cs

No physics engine, no collider components, no collision events — just Rectangle.Intersect and arithmetic. The interesting question in Breakout is never whether the ball hit a brick, but which side it hit, because that decides which velocity component flips.

Minimal penetration

Source/Systems/CollisionHelper.csthe shallower overlap axis is the impact axis
Rectangle overlap = Rectangle.Intersect(moving, target);
if (overlap.IsEmpty)
    return HitSide.None;

if (overlap.Width < overlap.Height)
    return moving.Center.X < target.Center.X ? HitSide.Left : HitSide.Right;

return moving.Center.Y < target.Center.Y ? HitSide.Top : HitSide.Bottom;

If the overlap rectangle is wider than it is tall, the ball came in vertically, and vice versa. Relative centers disambiguate which of the two sides. After detection, PlayingState.ReflectAndSeparate pushes the ball out by the overlap and sets the velocity sign (rather than negating it) — setting is idempotent if a collision ever resolves twice.

DESIGN NOTE

This discrete test is only safe because the numbers say so: max ball speed 560 px/s ÷ 60 Hz ≈ 9 px per tick, against 20 px bricks — tunneling is impossible. Crank the speed past ~1200 px/s and you'd need a swept test. Professional code isn't code without simplifications; it's code whose simplifications are justified and written down.

The aiming paddle — the game-feel heart

Source/Entities/Ball.cswhere you hit decides where it goes
float offset = (Position.X - p.Center.X) / (p.Width / 2f);
offset = MathHelper.Clamp(offset, -1f, 1f);

float angle = offset * MaxBounceAngle;   // 60° from vertical at the edge
Velocity = new Vector2(MathF.Sin(angle), -MathF.Cos(angle)) * Speed;

The exit angle ignores the incoming angle entirely — it's a pure function of where the ball struck the paddle. Center: straight up. Edge: 60°. This single mapping turns the paddle from a wall into an aiming device, and it's the knob of the whole genre. Also note the two anti-stick guards: paddle bounce only triggers while the ball descends, and brick resolution handles one brick per tick.

TRY IT

Change MaxBounceAngle to MathHelper.Pi / 6f (30°) and play a round. Then try 75°. Feel how the game changes from "passive" to "twitchy" with one constant — that's game feel living in a single number.

07 / ARCHITECTURE

States Without Scenes

open: Source/States/*.cs · Source/GameSession.cs

Ready → Playing → LifeLost → GameOver, with Pause and LevelCleared joining the loop where needed. Engines ship a scene system or a state machine node for exactly this; MonoGame ships neither, so you write the pattern yourself — about 30 lines — and in exchange you see exactly what a "screen change" is: swapping which object gets the Update and Draw calls. Two refinements worth tracing: PauseState keeps the state it interrupted and swaps it back without re-running Enter(), and the FreezesEffects flag lets pause stop even the particles every other state animates.

Source/States/GameStateManager.csa scene changer is just a field assignment
public void ChangeState(GameState next)
{
    _current = next;
    next.Enter();
}

public void Update(float dt, InputHelper input)
{
    if (!_current.FreezesEffects)
        Session.UpdateEffects(dt); // effects run in (almost) every state
    _current.Update(dt, input);
}

The crucial split: data vs. behavior

GameSession owns the world — paddle, balls, bricks, score, lives, level index, particles. States are modes of operating on that world. That's why the ball sits frozen mid-air on the game-over screen and the HUD stays visible during the life-lost flash: switching states never copies, rebuilds, or hides the world. "New game" is one line: Session = new GameSession().

MENTAL MODEL

Engine scene switching usually destroys the old scene — which is why carrying a score across screens pushes you toward global singletons. Here persistence is the default and you opt out by constructing fresh, which is the less bug-prone direction.

DESIGN NOTE

Notice what this project deliberately does not have: no ECS, no DI container, no event bus. Breakout doesn't need architecture; it needs clarity. Knowing how much structure a game does not need is a professional skill.

08 / PRODUCTION RENDERING

The Virtual Screen

open: Source/Systems/VirtualScreen.cs · BreakoutGame.cs (Draw, OnClientSizeChanged, ToggleFullscreen)

The single most instructive piece of "real project" infrastructure. Gameplay thinks in 800×480 forever; the window can be anything. The trick is a two-pass draw:

BreakoutGame.csrender to target, then present scaled
// Pass 1: the whole game, into the 800x480 render target.
_virtualScreen.BeginDraw();          // SetRenderTarget(target)
GraphicsDevice.Clear(ClearColor);
_spriteBatch.Begin(samplerState: SamplerState.PointClamp,
                   transformMatrix: _states.Session.Shake.TransformMatrix);
_states.Draw(_spriteBatch);
_spriteBatch.End();

// Pass 2: the render target onto the real back buffer, letterboxed.
_virtualScreen.Present(_spriteBatch); // SetRenderTarget(null) + draw scaled

A RenderTarget2D is a texture you can draw into; passing null to SetRenderTarget means "the actual back buffer". DestinationBounds scales by the smaller axis ratio (so the image always fits) and centers — the leftover area is the black letterbox bars.

The inverse problem: the mouse

The OS reports the mouse in window pixels; the game thinks in virtual pixels. Every scaled-rendering setup must apply the inverse transform — VirtualScreen.WindowToVirtual — exactly once, in one place (InputHelper.Update). Forget this and your paddle drifts away from the cursor the moment someone resizes the window.

MENTAL MODEL

In most engines this whole section is one project setting with a name like "stretch mode: keep aspect". Building it by hand once means that setting will never be magic again — and you'll know exactly why mouse coordinates go wrong whenever scaled rendering is misconfigured, in any engine.

GOTCHA ×2

1. DesktopGL does not resize the back buffer when the user resizes the window — OnClientSizeChanged does it manually, with a re-entrancy guard because ApplyChanges() re-fires the event. 2. Fullscreen here is borderless (HardwareModeSwitch = false): instant, flicker-free, alt-tab friendly. Exclusive mode only earns its pain when you need every millisecond of latency.

09 / GAME FEEL

Juice: Shake, Sparks, Square Waves

open: Source/Systems/ScreenShake.cs · ParticleSystem.cs · AudioBank.cs

Trauma-based screen shake

Impacts add trauma (0–1, capped); displayed intensity is trauma²; trauma decays linearly. The squaring is the magic: small hits barely register, big hits kick, and stacked hits compose naturally. The shake is applied as a translation matrix in SpriteBatch.Begin — the world draws shifted, the world's data never moves.

Particles without garbage

Source/Systems/ParticleSystem.csstructs: read, modify, write back
for (int i = 0; i < _particles.Count; i++)
{
    Particle p = _particles[i];   // List<T> indexer returns a COPY of a struct
    p.Velocity.Y += Gravity * dt;
    p.Position += p.Velocity * dt;
    p.Age += dt;
    _particles[i] = p;            // ...so write it back
}

Particles are structs so emitting hundreds allocates nothing the GC must chase. The copy-mutate-writeback dance is the price; C# won't let you mutate a struct inside a list in place, and knowing why (the indexer returns a copy) inoculates you against a whole family of "my changes don't stick" bugs.

SFX from raw PCM

SoundEffect happily accepts a byte buffer of 16-bit PCM — so AudioBank synthesizes every sound at startup: square waves with a 2 ms attack (kills the click) and linear decay, frequency sweeps for the life-lost fall and power-up rise. The normal route is .wav files through the pipeline; this is the "asset-free retro" route, and it teaches what a sound is.

GOTCHA

SoundEffect is for fire-and-forget polyphonic SFX. Music is a different API entirely: Song + MediaPlayer, streamed, one at a time. Loading music as a SoundEffect decompresses the whole file into RAM. Don't mix them up.

TRY IT

Press F3 in game and watch the particle count while you break a brick. Then open PlayingState.HandleBrickCollision and raise the emit count from 18 to 200 — watch the count spike and the FPS not care. That's the struct pool earning its keep.

10 / HABITS

Production Habits Hiding in Small Diffs

open: GameSession.DrawHud · ScreenShake.Update · BreakoutGame.Update · Source/Screen.cs

HabitWhereThe lesson
GC awareness GameSession.DrawHud $"SCORE {Score}" allocates a string. At 60 fps that's garbage the collector must sweep — so the HUD caches and rebuilds only when the value changes. Contrast: DebugOverlay allocates every frame on purpose and says why (debug tool, off by default). Same operation, two judgment calls.
Pure getters ScreenShake The RNG rolls once per tick in Update(); TransformMatrix just reads stored state. A getter returning different values on consecutive reads means two consumers in one frame silently disagree — a real bug class, not style pedantry.
Focus pause BreakoutGame.Update MonoGame keeps calling Update when the window is unfocused — pausing is your job. The IsActive early-out means nobody loses a ball while alt-tabbed. base.Update still runs for framework housekeeping.
Dependency direction Source/Screen.cs Screen constants used to live on the Game class, so a Brick depended on the application shell to learn the screen width. Now they're plain constants in their own type, and the shell is the only class nothing references.
Graceful degradation AudioBank.Initialize No audio device? Catch NoAudioHardwareException, leave the properties null, and every call site uses ?.Play(). The game runs silent instead of crashing.
Honest naming BreakoutGame.cs The template's Game1 is a placeholder, not a name. (Stardew Valley famously shipped with it — nothing breaks; it's still the first thing professionals rename.)
STILL OPEN — ON PURPOSE

Two known smells are left as discussion pieces: the static AudioBank/SpriteBatchExtensions (convenient at this scale; the alternative is passing them as dependencies — ask to see the comparison) and LevelLoader's total trust in well-formed files (production code would validate and report line numbers). Knowing a tradeoff exists beats pretending the code is finished.
